# 技术方案说明

更新日期：2026-06-01

本文描述当前 Android App 与 `/data/code/backup/ca-server` 的实际对接实现。旧版文档中关于用户标识字段、随机安装实例 ID、Tink Envelope DEK 以及 HTTP JSON 上传的描述不再适用于当前代码。

## 1. 总体架构

```
Android App
  SensorCollectorImpl
    -> SensorDataProcessor
    -> SerializedSensorBatch(Protobuf)
    -> LZ4 frame compression
    -> EnvelopeCryptoBox AES-256-GCM
    -> DataPacket(Protobuf)
    -> UploadManager / UploaderImpl
    -> gRPC SensorDataService.StreamSensorData
ca-server
  -> decrypt IV(12)|TAG(16)|ciphertext
  -> decompress LZ4/GZIP
  -> parse SerializedSensorBatch
  -> store raw packet
  -> optional authentication inference
  -> ServerDirective(Ack/PolicyUpdate/AuthResult)
```

- 主通信协议：gRPC 双向流 `SensorDataService.StreamSensorData`。
- 默认服务端端口：`10500`，与 server `src/config.py` 的 `grpc_port` 一致。
- App 默认公网入口：`https://ty.macrz.com:10500`，页面仍允许手动修改。
- 加密上传：先序列化、再压缩、最后加密。服务端解密顺序与此相反。
- 认证 UI：模型名称、认证结果、窗口、阈值、分数、EMA / y-of-x 文本均来自服务端 `StartAuthentication` 或 `AuthResult`。

## 2. 关键模块

| 模块 | 文件 | 说明 |

## 3. 上传标识 HMAC

当前 App 不再维护用户 ID。服务端路径与模型入口使用 `device_id_hash` 作为设备级标识。

`EnvelopeCryptoBox.getDeviceIdHash()` 的流程：

1. 构造稳定设备材料，按优先级选择单一来源：
   - 优先使用 Widevine `PROPERTY_DEVICE_UNIQUE_ID` 的 SHA-256 摘要；
   - 若设备不支持 Widevine 唯一材料，使用 `Settings.Secure.ANDROID_ID`；
   - 若上述值都不可用，才回退到 `Build.MANUFACTURER`、`BRAND`、`DEVICE`、`PRODUCT`、`MODEL`、`BOARD`、`HARDWARE`。
2. HMAC key 固定派生：`SHA-256("Continuous_Authentication:hmac:v1")`。
3. HMAC 输入带域隔离：`"ca-device-upload-id-v1:<stable-device-material>"`。
4. 输出采用 URL-safe Base64，避免服务端把标识作为目录名时出现 `/`。

前台应用包名不明文上传。`SensorSample.foreground_app_hash` 使用同一 HMAC key，但域为 `ca-foreground-app-v1`。

说明：该方案不依赖 App 私有存储中的随机值，因此普通卸载重装后保持稳定。若系统重置 DRM 标识、恢复出厂设置、系统多用户切换或 ROM 对 Widevine / `ANDROID_ID` 行为做特殊限制，平台层仍可能改变底层材料。

## 4. 数据协议

App 与 server 使用同名 `sensor_data.proto`。当前关键字段如下：

```proto
message DataPacket {
  string packet_id = 1;
  string device_id_hash = 2;
  int64 base_wall_ms = 3;
  int64 device_uptime_ns = 4;
  optional int64 ntp_offset_ms = 5;
  bytes encrypted_sensor_payload = 6;
  bytes encrypted_dek = 7;
  string dek_key_id = 8;
  Metadata metadata = 9;
  int64 packet_seq_no = 10;
  bytes sha256 = 11;
}

message SerializedSensorBatch {
  repeated SensorSample samples = 1;
  string session_id = 3;
}

message SensorSample {
  SensorType type = 1;
  int64 event_timestamp_ns = 2;
  float x = 3;
  float y = 4;
  float z = 5;
  int32 accuracy = 6;
  int64 seq_no = 7;
  string foreground_app_hash = 8;
}
```

`SerializedSensorBatch` 当前只包含 `samples` 和 `session_id`。不存在用户标识字段。

`encrypted_sensor_payload` 的格式与 server `AESDecryptor` 一致：

```
IV(12 bytes) || TAG(16 bytes) || CIPHERTEXT
```

其中 `CIPHERTEXT` 是 LZ4 压缩后的 `SerializedSensorBatch.toByteArray()`。服务端也支持 GZIP 自动识别，但 App 当前默认发送 LZ4。

## 5. 认证链路

认证启动：

1. App 已连接 gRPC 并启动加密上传后，调用 `StartAuthentication(AuthSessionRequest)`。
2. 请求字段：`device_id_hash`、`session_id`、`app_version`、`android_api_level`。
3. 服务端返回 `accepted`、`message`、`session_id`、`model_version`、`window_size_sec`、`decision_time_sec`。
4. App 只展示服务端返回的数据，不在端侧推断模型名或策略结果。

认证结果：

1. 服务端在 gRPC 流中下发 `ServerDirective.auth_result`。
2. App 校验 `session_id` 和 `device_id_hash`，只处理当前上传会话的结果。
3. UI 使用 `normalized_score`、`threshold`、`accept`、`interrupt`、`window_id`、`window_size_sec`、`model_version`、`message`、`server_timestamp_ms`。
4. EMA 或 y-of-x 细节当前由 server 放入 `message`，App 原样展示。
5. 持续认证页在“近期判定”下方展示“恶意用户检测日志”，每次成功启动认证会话后重新记录前 10 次 `accept=false` 的结果，包含具体时间和相对当前时间。

## 6. Server 处理要点

server gRPC 路径在 `src/grpc_server.py`：

- `GetInitialPolicy` 下发 LZ4、批次窗口、传感器采样率等策略。
- `StreamSensorData` 接收 `DataPacket`，按 `encrypted_sensor_payload` 执行解密、解压、解析。
- `StartAuthentication` 按 `device_id_hash` 查找模型或触发训练准备。
- `_run_auth_inference` 生成 `AuthResult`，包括阈值、窗口、模型版本和判定消息。

server 加密配置在 `src/config.py`，默认 `encryption_key = "Continuous_Authentication"`，与 App `EnvelopeCryptoBox` 的 AES-GCM 派生密钥一致。

## 7. 本地存储与隐私

- `BatchMetadata` Room schema 当前版本为 2，已移除运行时批次记录中的用户标识字段。
- v1 schema 文件保留旧数据库历史结构，仅用于 Room schema 记录，不代表当前运行时协议。
- 撤回同意会停止上传、清理本地缓存与会话数据。
- App 不上传明文设备 ID、明文前台应用包名或用户 ID。
