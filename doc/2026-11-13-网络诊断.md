# ca.macrz.com 连通性检查（2026-11-13）

北京时间 15:58 起实测：公网入口 `https://ca.macrz.com:443` 能建立可信 TLS/HTTP2 连接，但 App 使用的真实 gRPC 心跳收到 OpenResty 的 HTTP 504，当前不能完成业务连接。本机后端同一心跳正常，故障范围集中在公网代理及其回源链路。

本次仅检查连接与心跳，没有启动认证会话、传感器采集或上传，也没有修改 App 源码、服务配置或重启服务器。

## 原因判断与证据边界

已确认公网 OpenResty 返回 HTTP 504 网关超时，本机后端 RPC 正常。现有证据支持优先排查代理回源地址、路由、防火墙和转发隧道，而非修改 App 的 TLS 校验或增加客户端等待时间。

服务端仓库模板 `deploy/openresty/proxy/grpc_10500.conf:12` 使用 `grpc_pass grpc://127.0.0.1:10500`，连接超时为 `2s`。该超时与本次约 2.05 秒的 504 相符，提示上游建连超时；但模板并非公网生效配置，不能据此断言当前上游写成了 localhost 或确定某个具体地址错误。代理中的 localhost 仅在该网络命名空间确有后端或隧道 visitor 监听时才有效。

额外线索：

- `ty.macrz.com → 203.25.212.99`；本机至其 `10500` TCP 连接 4 秒超时，h2c 心跳 15 秒超时。这只说明本机到该地址不通，不能代替公网代理所在网络的测试，也不能证明公网当前仍使用此上游。
- 本机 `frpc-99-ca10500-source.service` 于今天 15:07:48 CST 启动，当前 active/running，描述为 `frp STCP source for CA gRPC 10500 to 99 via 175`。进程存活不能证明 source、visitor、服务端注册及转发链路正常；STCP 也不意味着公网必须直接开放后端端口。
- FRP 精确配置和系统日志当前用户无读取权限，非交互 sudo 提示需要密码；未取得其中非敏感目标字段与错误日志。公网 OpenResty 的生效配置与错误日志尚未取得，因此具体是哪一段地址、隧道或防火墙故障仍未证实。

## 下一步定位

1. 在公网 OpenResty 主机或容器内读取 `nginx -T` / `openresty -T`，确认该域名及 RPC 路径实际命中的 `grpc_pass`。
2. 对照本次请求时间（约 07:59 UTC / 15:59 北京时间）读取 error.log 的 upstream 地址及错误阶段，区分连接超时与读取响应超时。
3. 在同一网络命名空间向实际 upstream 发只读 Health 或 SendHeartbeat，检查端口和路由；若经过 FRP/STCP，核对 source、对应 visitor 的注册日志、绑定地址与监听端口。
4. 当前本机后端使用 h2c，连接它的代理应使用匹配的 `grpc://`；只有后端实际开启 TLS 才使用 `grpcs://`。恢复转发链路后，通过公网 TLS 入口复测真实心跳。
